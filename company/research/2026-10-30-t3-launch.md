# T3 launch blockers: Drizzle connection and public authentication

Research date: 2026-10-30. Primary documentation only. Read the brief and both earlier research notes; consulted the Supabase skill and current changelog. No app edits, account changes, credential retrieval, cloud mutations, installs, or connection tests were performed. Project `dsbdvfweiookjvdwkpha` / `us-east-1` is supplied context, not newly verified project configuration.

## Recommendation

Activate Drizzle through the existing Supabase Free **shared transaction pooler**, using a dedicated restricted LOGIN role with its own generated password. Obtain the assigned host from the project's Connect dialog or the read-only Management API endpoint below; do not guess it from the region or request the user's `postgres` password.

For the developer-focused initial release, **GitHub OAuth is the smallest practical public sign-in path**. It still requires a real OAuth application, provider configuration, and a successful external-account test. If retaining public email/password signup at launch is required, use supported custom SMTP such as Resend Free with a verified sending domain. Neither path is ready merely because its button or environment variable exists.

These are implementation recommendations, not evidence of live functionality. tRPC, Drizzle, Next.js, TypeScript, and Tailwind remain the required application stack; Supabase Auth does not require introducing NextAuth to qualify as that stack in this product brief.

## A. Drizzle without the administrator's database password

### Supported connection shape

Supabase documents shared transaction pooling on Free over IPv4 at port `6543`. Custom-role usernames are `[ROLE].[PROJECT-REF]`; therefore an example role `tokenoverflow_app` connects as `tokenoverflow_app.dsbdvfweiookjvdwkpha`, with **that role's password**, to database `postgres`. The host contains a project-assigned cluster index; `aws-0-us-east-1.pooler.supabase.com` cannot safely be inferred. A region can contain several clusters. Copy the assigned host. Transaction pooling is intended for short serverless connections, and session state cannot be assumed to persist between transactions. [Connection guide](https://supabase.com/docs/guides/database/connecting-to-postgres), [host/username troubleshooting](https://supabase.com/kb/troubleshooting/tenant-or-user-not-found).

The supported Drizzle/Postgres.js integration uses `prepare: false` for shared transaction pooling. Keep the application-side pool small; the connection guide recommends starting at one rather than accepting Postgres.js's ten-connection default for every warm serverless instance. Use encrypted connections and keep the complete URI server-only. [Drizzle guide](https://supabase.com/docs/guides/database/drizzle), [prepared-statement guide](https://supabase.com/kb/troubleshooting/disabling-prepared-statements-qL8lEL).

### Exact host discovery options

1. **Existing authenticated Supabase Dashboard:** project → Connect → Transaction pooler. The displayed string contains the host and a password placeholder; viewing it does not require knowing or resetting the database password. Replace the username and password with the dedicated role's credentials when assembling the server environment value.
2. **Management API, if an independently authorized credential is already available:** `GET https://api.supabase.com/v1/projects/dsbdvfweiookjvdwkpha/config/database/pooler`. Official response fields include `db_host`, `db_port`, `db_name`, `db_user`, `pool_mode`, and `connection_string`. OAuth needs `database:read`; a fine-grained token needs `database_pooling_config_read`. Select the primary transaction-pooler result and retain only non-secret host/port metadata in logs. This endpoint uses Management API authorization, not a database administrator password. [Endpoint reference](https://supabase.com/docs/reference/api/v1-get-pooler-config).

The connected Supabase tool inventory offers project metadata and SQL but no pooler-config endpoint. Project region plus the direct `db.<ref>.supabase.co` hostname does not identify the shared host. Do not search local credential stores or extract connector tokens to bridge this tool gap. A coordinator can use an authorized existing Dashboard session, or have the owner copy **only the pooler host** if no suitable management capability exists. No new token needs to be shared in chat.

### Dedicated-role scope

Supabase explicitly recommends a separate database user per external service; a role can have `LOGIN PASSWORD` independently of `postgres`. Grant only the needed database connection, schema usage, specific table reads, and explicitly approved function execution. Do not grant ownership, `BYPASSRLS`, admin role membership, schema creation, or broad write rights merely to make an ORM connection succeed. [Role guide](https://supabase.com/docs/guides/database/postgres/roles).

Important implementation inference: SQL login does not automatically supply the end user's Supabase JWT or `auth.uid()`. Existing authenticated writes must retain their authorization path, or use deliberate transaction-scoped identity handling with a reviewed policy design. A restricted Drizzle public-read path plus the established Supabase write path is a reasonable incremental activation; an unused Drizzle schema is not activation. Audit actual role permissions, including inherited `PUBLIC` grants: `NOINHERIT` alone does not remove those. [Custom-role privilege guide](https://supabase.com/kb/troubleshooting/custom-role-inherits-privileges-that-were-not-explicitly-granted).

Before claiming completion, demonstrate an actual deployed query through Drizzle using the dedicated role; inspect `current_user`; verify expected public rows and denial of an unauthorized table/write operation. Keep migration/admin credentials separate from runtime. This research did not choose exact table/function grants or perform these checks.

## B. Free public sign-in

### Present limitation

Hosted default SMTP is restricted to team-member email addresses and currently two messages per hour, with no delivery SLA. It is not public email delivery. Custom SMTP starts with a separate Supabase limit of 30 messages/hour; provider quotas also apply. Social sign-in configurations that explicitly require confirmation email still need delivery. Do not disable confirmation to disguise a delivery problem. [Supabase SMTP policy](https://supabase.com/docs/guides/auth/auth-smtp).

### Recommended first option: GitHub OAuth

Owner setup: register a GitHub OAuth App with homepage `https://tokenoverflow.app` and authorization callback `https://dsbdvfweiookjvdwkpha.supabase.co/auth/v1/callback`; enter its Client ID and generated secret in Supabase's GitHub provider settings. These secrets belong in provider settings, not repository files or client variables. The website starts `signInWithOAuth({ provider: 'github', options: { redirectTo: 'https://tokenoverflow.app/auth/callback' } })`; the existing app callback must exchange the PKCE code into cookies. Allowlist that exact app redirect. Provider callback and app callback are different URLs. [Supabase GitHub setup](https://supabase.com/docs/guides/auth/social-sign-in/auth-github).

Normal provider-confirmed GitHub sign-in avoids the email-confirmation send, making this a practical inference from the documented OAuth flow rather than an SMTP workaround. It requires a GitHub account and excludes email-only users. Test a fresh GitHub user outside the Supabase organization, including a private-email account, session persistence, signout, and a real authorized contribution. Do not promise unsupported scope or repository access: authentication does not need repo permissions. GitHub's documentation supports public OAuth user authorization, though it generally recommends GitHub Apps for broader integrations; this product's documented Supabase provider specifically uses an OAuth App. [GitHub OAuth authorization](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps), [scope meaning](https://docs.github.com/en/apps/oauth-apps/using-oauth-apps/connecting-with-third-party-applications).

Until SMTP exists, label or hide email signup and reset flows accurately. A GitHub-only public launch can be described as such after it passes; it cannot be described as working public email signup.

### Alternative: Resend Free custom SMTP

Current Resend Free quotas are 3,000 transactional emails/month and 100/day, shared by sent and received messages; daily reset is midnight UTC. Current docs allow **three verified domains**, superseding older one-domain posts. It is a free-forever plan; leave paid overages/upgrades disabled. [Current quota policy](https://resend.com/docs/knowledge-base/account-quotas-and-limits), [pricing](https://resend.com/pricing).

One-time setup: create/choose the owner's Resend account; verify a sending domain or subdomain using its exact supplied DNS records; create an API key; configure Supabase SMTP with host `smtp.resend.com`, port `465`, username `resend`, password equal to the API key, and a From address on the verified domain. A hosted mailbox is not a prerequisite stated by the integration guide. DNS verification and the API key are prerequisites; the testing sender alone is not a public production sender. [Official Supabase SMTP integration](https://resend.com/docs/send-with-supabase-smtp).

Resend currently states that Free accounts have immediate production access, with no production approval or waiting period; domain verification remains necessary. Do not import another provider's sandbox rules into this recommendation. [Production-access policy](https://resend.com/docs/knowledge-base/does-resend-require-production-approval).

After configuration, test confirmation to an address outside the Supabase team, the actual confirmation redirect/session, existing password login, and reset delivery. Confirm template/redirect choices described in the earlier launch memo. SMTP transport success alone does not prove inbox delivery or a usable app session. No Resend account, DNS, provider configuration, or external-address test was inspected or changed here.

## Owner's one-time GitHub sign-in setup

Rechecked 2026-10-30. GitHub's documented registration path is its website; its public REST OAuth endpoints manage existing tokens/grants. No documented public OAuth App registration endpoint was found. This is a connector/API capability gap, not a claim that browser assistance is impossible. Supabase also has an Auth Management API, but the current connected tools do not expose that configuration operation. [GitHub registration](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/creating-an-oauth-app), [REST OAuth endpoints](https://docs.github.com/en/rest/apps/oauth-applications).

1. Open [New OAuth App](https://github.com/settings/applications/new) while signed into the intended owner account. Review these public form values, then register:

   | Field | Value |
   | --- | --- |
   | Application name | Token Overflow |
   | Homepage URL | `https://tokenoverflow.app` |
   | Application description | Leave blank (optional) |
   | Authorization callback URL | `https://dsbdvfweiookjvdwkpha.supabase.co/auth/v1/callback` |
   | Enable Device Flow | Unchecked |

   Leave other options at their current defaults; no repository access is needed for sign-in. Current GitHub docs also mention an access-token expiry default; this app does not need long-lived GitHub API tokens merely to authenticate users.
2. On the registered app page, generate a client secret. Copy the Client ID and secret directly into [this project's Sign In / Providers page](https://supabase.com/dashboard/project/dsbdvfweiookjvdwkpha/auth/providers): expand **GitHub**, enable it, fill both fields, and save. No secret needs to be pasted into chat, committed, or added to public app variables. The documented route opens the providers page; a GitHub-specific accordion deep link was not verified. [Supabase GitHub guide](https://supabase.com/docs/guides/auth/social-sign-in/auth-github).
3. In [this project's URL Configuration](https://supabase.com/dashboard/project/dsbdvfweiookjvdwkpha/auth/url-configuration), set Site URL to `https://tokenoverflow.app` and add exact Redirect URL `https://tokenoverflow.app/auth/callback`. Preserve other intentional entries. This app URL is different from the Supabase callback registered at GitHub. [Redirect configuration](https://supabase.com/docs/guides/auth/redirect-urls).
4. Return to the app and test Continue with GitHub using an external account, then session persistence, signout, and an authorized contribution. Configuration saved is not yet a passing public sign-in test. These owner settings were not inspected or changed during research.
