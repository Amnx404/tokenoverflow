## Invalid-token redirect interpretation — bounded official-source review

**Answer:** the inspected official Auth/GoTrue implementation honors an accepted `redirect_to` even when the token is invalid; invalid-token failure does **not** itself force Site URL. Read source at immutable upstream commit `a7e97d665b9ea03853edb66d014bcde323f7894b` on 2026-10-30 PDT; this is not an identified hosted-service version. The [redirect documentation](https://supabase.com/docs/guides/auth/redirect-urls#error-handling) also describes failure returning to the supplied redirect with error details. No new project request, email/account write or configuration change was made.

The [GET verification handler](https://github.com/supabase/auth/blob/a7e97d665b9ea03853edb66d014bcde323f7894b/internal/api/verify.go#L95-L105) calls `GetReferrer` **before** verifying the token. [Redirect selection](https://github.com/supabase/auth/blob/a7e97d665b9ea03853edb66d014bcde323f7894b/internal/utilities/request.go#L75-L153) accepts a valid `redirect_to` (header first, then parsed query/form), otherwise a valid Referer, otherwise `config.SiteURL`. Validity includes the configured Site URL's scheme/hostname/port or an allowed URL pattern; pattern comparison uses the full URL except its fragment. The [verification error branch](https://github.com/supabase/auth/blob/a7e97d665b9ea03853edb66d014bcde323f7894b/internal/api/verify.go#L198-L209) passes that already-selected URL to [the error formatter](https://github.com/supabase/auth/blob/a7e97d665b9ea03853edb66d014bcde323f7894b/internal/api/verify.go#L491-L521), which preserves its destination and adds error details. Implicit flow puts errors in the fragment; PKCE also adds query parameters. Source tests [preserve the supplied error destination/query](https://github.com/supabase/auth/blob/a7e97d665b9ea03853edb66d014bcde323f7894b/internal/api/verify_test.go#L1196-L1243) and [show valid redirect versus Site URL fallback](https://github.com/supabase/auth/blob/a7e97d665b9ea03853edb66d014bcde323f7894b/internal/utilities/request_test.go#L245-L337). These tests were read, not run by research.

**Project inference and owner wording:** with this implementation and the described request, an accepted canonical callback would keep its origin/path on `otp_expired`. The observed legacy origin/root is consistent with the canonical target not being selected and a configured fallback being used. It is not evidence that invalid tokens universally ignore accepted redirects, nor proof of a particular missing/wrong allowlist entry, the actual Site URL value, or successful confirmation behavior. Hosted commit/proxy behavior and authenticated configuration are unobserved. Tell the owner: **inspect canonical Site URL and whether the actual callback URL including its `next` query is accepted; the invalid-token request returned a legacy destination, and source review makes selection/fallback a plausible explanation, not a diagnosed allowlist defect.** Same-origin acceptance may make an additional allowlist entry unnecessary once Site URL is canonical; do not infer a required config edit before inspection. ## Smallest code/deployment implications

Use the existing SSR PKCE flow and canonical safe return path. An accepted new-user signup initiates required confirmation; a generic successful signup response itself is not account creation or mail-delivery proof. Only a completed exchange and a fresh server-validated user establish the session. Match the actual email template to either the code-exchange callback or token-hash confirmation path, and verify the allowlist/Site URL. Do not assume the presence of both handlers proves the selected template reaches one correctly. [Password/PKCE guide](https://supabase.com/docs/guides/auth/passwords).

Relevant breaking change found in the required changelog scan: new Free projects using built-in SMTP since June 3, 2026 cannot customize email templates; earlier projects retain existing templates and custom SMTP allows customization. **This project's creation/template state is unknown.** Do not make a required token-hash-template edit the only route until the actual configuration is inspected; the existing callback can exchange a code if that is what the selected flow supplies. [Official change](https://supabase.com/changelog/46599-changes-to-email-template-customisation-on-free-tier).

For password recovery, the supported path is `resetPasswordForEmail` → allowlisted recovery destination → recovered authenticated session → `updateUser({password})`. A no-error reset request is intentionally non-enumerating and may send nothing when no user exists; it is not delivery proof. Static source at review shows `app/auth/confirm/route.ts` accepts only `email|signup`, not `recovery`: do not route a recovery token-hash template there unchanged. Maya (Backend engineer)/Rafael (Engineering lead) choose the bounded recovery handler/UI when that slice is shipped; no research-driven auth redesign is required.
