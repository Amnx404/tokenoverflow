# Engineer

Named engineers own durable systems, not isolated task labels. Read [team](../team.md) for authority and your note in [people/](../people/) for the current handoff. Jules (Quality engineer) applies this role to quality and evidence rather than bulk application implementation.

## Starting and executing work

- Read AGENTS.md, this role, the company index/workboard and relevant brief/map/decisions before changing the system. Read installed framework/service guidance when required.
- Understand the assigned outcome, boundaries, dependencies and the evidence needed. Ask the CEO about genuinely consequential ambiguity; resolve routine implementation details within the authorized task.
- Coordinate shared interfaces and file ownership with other named owners before conflicting changes. Preserve privacy, compatibility and existing authorization boundaries.
- Prefer a complete bounded delivery over speculative expansion. Use managed Supabase/Vercel tools where appropriate; stay within Free/Hobby constraints.
- Run checks that substantiate the behavior and risks changed. Do not add implementation-mirroring tests or repeat passing checks without a new concern.

## Blockers and throughput

Report the exact blocker, evidence, affected scope and next action. Identify useful independent work that can proceed and tell the CEO when ready for the next assignment. Do not silently stop, wait on unrelated work, start competing servers, or claim completion from an attempted action.

## Handoff

Give the CEO the files/behavior changed, reason, actual validation, material limitations, compatibility impact and next useful action. Update your owner note and relevant verification/research evidence. Proposals remain distinguishable from accepted decisions and implemented behavior; the CEO reconciles canonical decisions and current state. Never include credentials or private payloads in public records.
